# Nadia_Project

## Лабораторна робота №4

Тема: інтеграція фронтенду з бекендом.

Варіант 11: **Сервіс чергувань у лабораторії**. Основна сутність для інтеграції: **Shifts**.

Фронтенд і бекенд запускаються як два окремі процеси на різних портах:

- Backend: `http://localhost:3000`
- Frontend: `http://localhost:5500`
- API base URL: `http://localhost:3000/api/v1`

## Що реалізовано для ЛР4

### Рівень «задовільно»

- Frontend читає реальні дані з бекенду через `fetch`.
- Реалізовано два GET-запити:
  - `GET /api/v1/shifts` — список чергувань;
  - `GET /api/v1/shifts/:id` — деталі одного запису.
- Дані виводяться у таблицю з полями `date`, `timeSlot`, `userName`, `comment`, `status`.
- Є стани інтерфейсу: loading, success, empty, error.
- Є константа `API_BASE_URL`, URL бекенду не розкиданий по коду.
- CORS налаштовано через whitelist origin, а не через `*`.

### Рівень «добре»

- Додано CRUD-інтеграцію:
  - `POST /api/v1/shifts` — створення;
  - `PUT /api/v1/shifts/:id` — редагування;
  - `DELETE /api/v1/shifts/:id` — видалення.
- Усі запити проходять через єдиний модуль `Frontend/src/apiClient.ts`.
- На бекенді є валідація DTO через Zod.
- Є централізована обробка помилок і єдиний формат помилки.
- Після створення, редагування або видалення список оновлюється через повторний запит до API.
- Є UX-захист: блокування кнопок під час запиту та підтвердження видалення.

### Рівень «відмінно»

- Frontend написаний на TypeScript.
- DTO описані у `Frontend/src/dtos.ts`.
- API має версіонування через `/api/v1`.
- Опис контрактів і правил сумісності є в `docs/contracts.md`.
- Реалізовано таймаут запиту через `AbortController`.
- UI коректно обробляє погані сценарії: бекенд вимкнений, HTTP 400/404/409/500, помилки валідації.
- README містить відтворювані сценарії перевірки.

## Запуск бекенду

У WebStorm відкрийте термінал у папці `Backend`:

```bash
cd Backend
npm install
npm run migrate
npm run seed
npm run dev
```

Після запуску API буде доступне за адресою:

```text
http://localhost:3000/api/v1/health
```

## Запуск фронтенду

Відкрийте другий термінал у WebStorm у папці `Frontend`:

```bash
cd Frontend
npm install
npm run build
npm run serve
```

Після цього відкрийте у браузері:

```text
http://localhost:5500/Main.html
```

Фронтенд не потрібно відкривати подвійним кліком як `file://`, бо для ЛР4 він має запускатися через локальний вебсервер.

## Сценарії перевірки

### 1. Перевірити GET-список

1. Запустити бекенд і фронтенд.
2. Відкрити `http://localhost:5500/Main.html`.
3. Переконатися, що таблиця заповнилася даними з seed.
4. У DevTools → Network має бути запит:

```text
GET http://localhost:3000/api/v1/shifts
```

### 2. Перевірити GET-деталі

1. У таблиці натиснути кнопку «Деталі».
2. Праворуч/знизу має з’явитися блок із деталями запису.
3. У Network має бути запит:

```text
GET http://localhost:3000/api/v1/shifts/1
```

### 3. Перевірити POST

1. Заповнити форму.
2. Натиснути «Додати».
3. Має з’явитися повідомлення «Запис створено».
4. Таблиця має оновитися без перезавантаження сторінки.

### 4. Перевірити PUT

1. Натиснути «Редагувати» біля запису.
2. Змінити коментар або статус.
3. Натиснути «Зберегти».
4. Таблиця має оновитися через API.

### 5. Перевірити DELETE

1. Натиснути «Видалити».
2. Підтвердити видалення.
3. Запис має зникнути з таблиці.

### 6. Перевірити помилку валідації 400

1. Очистити поле «Користувач» або залишити дуже коротке ім’я.
2. Натиснути «Додати».
3. Frontend має показати помилку біля поля.

### 7. Перевірити конфлікт 409

1. Спробувати створити чергування з тією самою датою, часовим слотом і користувачем, що вже є в таблиці.
2. Backend поверне `409`.
3. Frontend покаже повідомлення про помилку.

### 8. Перевірити мережеву помилку / CORS / таймаут

1. Зупинити бекенд.
2. Оновити сторінку фронтенду або натиснути «Оновити з API».
3. UI не повинен ламатися. Має з’явитися повідомлення про помилку мережі або CORS.
