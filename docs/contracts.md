
# DTO-контракти для лабораторної роботи №4

## Версія API

Усі запити фронтенду використовують стабільний префікс:

```text
/api/v1
````

Зміни, які можуть зламати сумісність із фронтендом, дозволено робити тільки в новій версії API, наприклад:

```text
/api/v2
```

---

## ShiftDto

Відповідь для запитів:

```text
GET /api/v1/shifts
GET /api/v1/shifts/:id
```

```ts
interface ShiftDto {
  id: number;
  date: string;
  timeSlot: string;
  userName: string;
  comment?: string | null;
  status: "planned" | "done" | "canceled" | string;
}
```

### Опис полів

* `id` — унікальний ідентифікатор запису.
* `date` — дата чергування у форматі `YYYY-MM-DD`.
* `timeSlot` — часовий слот чергування.
* `userName` — ім’я користувача, який виконує чергування.
* `comment` — коментар до чергування. Поле може бути порожнім або `null`.
* `status` — статус чергування: `planned`, `done`, `canceled`.

## CreateShiftDto

Тіло запиту для створення запису:

```text
POST /api/v1/shifts
```

```ts
interface CreateShiftDto {
  date: string;
  timeSlot: "08:00-10:00" | "10:00-12:00" | "12:00-14:00" | "14:00-16:00" | "16:00-18:00";
  userName: string;
  comment?: string;
  status: "planned" | "done" | "canceled";
}
```

### Правила валідації

* `date` — обов’язкове поле.
* `timeSlot` — обов’язкове поле, значення має бути одним із дозволених часових слотів.
* `userName` — обов’язкове поле, довжина від 2 до 60 символів.
* `comment` — необов’язкове поле, максимальна довжина 200 символів.
* `status` — обов’язкове поле, значення має бути `planned`, `done` або `canceled`.

## UpdateShiftDto

Тіло запиту для редагування запису:

```text
PUT /api/v1/shifts/:id
```

```ts
interface UpdateShiftDto {
  date: string;
  timeSlot: "08:00-10:00" | "10:00-12:00" | "12:00-14:00" | "14:00-16:00" | "16:00-18:00";
  userName: string;
  comment?: string;
  status: "planned" | "done" | "canceled";
}
```

`UpdateShiftDto` має таку саму структуру, як і `CreateShiftDto`, але використовується для оновлення вже існуючого запису.

## ApiError

Формат помилки, який повертає бекенд і обробляє фронтенд:

```ts
interface ApiError {
  status: number;
  code: string;
  message: string;
  detail?: string;
  errors?: Record<string, string[]>;
}
```

### Опис полів

* `status` — HTTP-статус помилки, наприклад `400`, `404`, `500`.
* `code` — короткий код помилки.
* `message` — зрозуміле повідомлення для користувача або розробника.
* `detail` — додаткові технічні деталі.
* `errors` — помилки валідації по конкретних полях форми.

## Правила сумісності DTO

Щоб не ламати роботу фронтенду, у версії `/api/v1` дотримуються такі правила:

1. Не можна перейменовувати або видаляти поля, які вже використовує фронтенд.
2. Не можна змінювати типи існуючих полів, наприклад `id: number` на `id: string`.
3. Нові поля можна додавати тільки як необов’язкові або з дефолтними значеннями.
4. Якщо потрібна несумісна зміна формату, її треба робити в новій версії API, наприклад `/api/v2`.
5. Фронтенд має використовувати дефолтні значення для `null` або `undefined`, щоб інтерфейс не ламався через неповні дані.
